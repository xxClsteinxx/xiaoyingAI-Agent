# 05 项目复盘

## 最难的问题

最难的不是把四个工具串起来，而是划清“模型自由决策”和“业务不可违反约束”的边界。只在提示词里要求模型不要越权并不可靠，因此将风险复核、时段占用、硬性时间、待确认和幂等约束都下沉到工具层；最终输出再与真实工具观察对账，防止模型通过文字虚报成功。

第二个难点是同时满足离线可复现和真实 ReAct 接入要求。解决方式是让同一个 Agent 循环依赖统一决策接口：离线策略用于无密钥测试工程链路，Responses API 适配器用于真实模型逐轮选择动作；输出显式标记 `real_model`，避免把 Mock 流程证据夸大为模型能力证据。

## 工程结论

- Agent 的关键是根据工具观察改变下一动作，而不是使用了哪个框架。
- 风险类系统适合让模型做语义选择，让确定性代码守住不可违反的约束。
- Trace 应记录可审计的业务依据，而不是模型内部思维过程。
- 幂等不仅是“查到就返回”，还必须校验同一请求 ID 的载荷是否一致。
- 保存失败、未尝试保存与保存成功必须使用不同终态，不能只靠自然语言说明。
- 离线 Mock 能证明流程和护栏，但不能证明真实模型的动态决策质量。

## 验证中发现并改进的问题

第一次直接运行示例生成脚本时，Python 的模块搜索路径只包含 `scripts/`，导致无法导入 `src`。修复方式是在脚本入口显式加入项目根目录，并重新生成全部验证材料。

进一步审查发现，只靠模型传入 `review_status=approved` 会留下绕过审核的可能。最终在 `save_draft` 内部重新执行规则检查，同时校验时段占用和硬性时间要求；最终结果层也会根据实际工具观察覆盖模型的不实成功表述。新增测试验证模型谎报审核和保存占用时段均会被拒绝。
